| المطلوب | ما نُفِّذ |
|---|---|
| إشعار فوري لجميع المشرفين عند تسجيل مستخدم جديد (FCM) | Trigger على `public.profiles` (بعد `INSERT`) → `push_call_edge` → دالة `send-push` توزّع الإشعار على **كل المشرفين (is_admin أو is_super_admin غير محظورين) على كل أجهزتهم** |

## 2) بنية الجداول الحالية (ما فُحص فعلياً قبل التنفيذ)

| الجدول | الدور في هذه الميزة |
|---|---|
| `public.profiles` | مصدر الحقيقة للمستخدمين. لا يوجد عمود `role`؛ الصلاحية عبر `is_admin` / `is_super_admin` (والحظر `is_blocked`). الصف يُنشأ تلقائياً بـ `handle_new_user()` عند إنشاء `auth.users` |
| `public.conversations` | `unique (user_id, admin_id)` ⇒ إنشاء محادثة مع أي مستخدم عملية **idempotent** لا تُنتج تكراراً |
| `public.fcm_tokens` | صف لكل جهاز/متصفح (`user_id`, `token` فريد, `device_id`, `device_info`) — الإشعار يذهب لكل صفوف المستلم |
| `public.push_delivery_log` + `public.push_call_edge()` | مسار pg_net + Vault (`SEND_PUSH_URL` / `SEND_PUSH_SECRET`) المستخدم أصلاً لرسائل ومكالمات الخلفية |
| RLS | `profiles readable by authenticated` ⇒ لا حاجة لسياسة جديدة لقراءة الدليل؛ والكتابة على `conversations` متاحة لأي من الطرفين |

**لا حاجة لأي جدول جديد** ولا لتغيير أي سياسة RLS: الميزتان تُبنَيان فوق البنية القائمة.

## 3) الميزة 1 — إشعار المشرفين عند تسجيل مستخدم جديد

### 3.1 التصميم: طلب واحد من قاعدة البيانات، وتوزيع داخل الدالة

المسار البديل الآخر (Webhook لكل مستخدم) كان سيُنتج **طلب شبكة لكل تسجيل**، وأسوأ منه: طلب لكل مشرف. التصميم المختار:

```
INSERT في profiles (تسجيل جديد)
        │  trigger: on_profile_created_notify_admins
        ▼
public.notify_admins_new_profile()      ← يتحقق من وجود مشرف نشط، ثم
        │  perform push_call_edge('new_user', new.id, null, <payload>)
        ▼
pg_net → POST  send-push { type: "new_user", user_id, display_name, email, phone, … }
        ▼
send-push: loadAdminIds()  (is_admin أو is_super_admin، غير محظورين)
           loadDeviceTokensForUsers(adminIds)   ← استعلام واحد لكل التوكنات
        ▼
FCM → كل أجهزة كل مشرف (data-only، أولوية عالية)
```

* **طلب pg_net واحد لكل تسجيل** مهما كان عدد المشرفين أو أجهزتهم.
* **حَلّ محلّ Webhook**: التطبيق لا يملك خدمة خارجية (Vercel Functions مثلاً)؛ الـ trigger + `pg_net` هو النمط المستخدم أصلاً في المشروع (`notify_new_message`, `notify_call_room`)، فلا تتفاوت المسارات.
* **لا خدمة جديدة تُنشر** بجانب `send-push`؛ أُضيف إليها فرع `new_user` فقط.

### 3.2 حمولة الإشعار

```jsonc
{
  "type": "new_user",
  "user_id": "<uuid>",           // مفتاح التوجيه: نقرة الإشعار تفتح محادثة معه
  "display_name": "سارة العتيبي",
  "email": "…" | null,           // البريد التقني phone.<digits>@users.local يُستبعد دائماً
  "phone": "+9665…" | null,
  "is_admin": false,             // true ⇒ «🛡️ مشرف جديد» بدل «👤 مستخدم جديد»
  "admins_count": 18,
  "created_at": "2026-10-13T19:00:00Z"
}
```

ويُبنى نص الإشعار في الدالة:

* العنوان: `👤 مستخدم جديد: <الاسم>` (أو `🛡️ مشرف جديد: <الاسم>`).
* النص: `انضم إلى التطبيق — <البريد أو الهاتف> — اضغط لبدء محادثة`.

### 3.3 الحالات الطرفية (مُتحقَّق منها بالاختبار على PostgreSQL حقيقي)

| الحالة | السلوك |
|---|---|
| لا يوجد مشرف نشط بعد | لا يُرسل شيء، ويُسجَّل `SKIPPED: لا يوجد مشرف مسجَّل/نشط بعد` في `push_delivery_log` |
| مشرف محظور | يُستبعد من `admin_recipient_ids()` ومن `loadAdminIds()` |
| فشل الإشعار (Vault غير مضبوط، تعذّر الشبكة، أي خطأ SQL) | **لا يُفشل التسجيل إطلاقاً**: `exception → raise warning` (نفس مبدأ `notify_new_message`) |
| تحديث الملف الشخصي لاحقاً | لا إشعار (`AFTER INSERT` فقط) — لا تكرار عند أول دخول لصفٍّ قائم |
| مستخدم مسجَّل برقم الهاتف | يُخفي البريد الداخلي `phone.<digits>@users.local` من الحمولة |
| مشرف يسجّل حساباً جديداً | يُشعر به بقية المشرفين كـ «مشرف جديد» (والمستلم نفسه يُستبعد من التوزيع) |
| أي مشرف لم يُفعّل الإشعارات | يُتخطّى (لا توكن)، ويُعاد `{ admins, sent: 0, skipped: "no fcm token" }` بلا خطأ |

### 3.4 المتطلبات المسبقة (نفس مسار رسائل الخلفية)

1. تنفيذ الهجرة `2026-10-13_v2_8_admin_new_user_alerts_directory.sql` (أو `schema.sql` كاملاً).
2. وجود `SEND_PUSH_URL` و`SEND_PUSH_SECRET` في Supabase Vault (وإلا يُسجَّل `SKIPPED`).
3. إعادة نشر الدالة بنسختها الجديدة: `supabase functions deploy send-push --no-verify-jwt`.
4. تفعيل الإشعارات عند كل مشرف (زر «تفعيل إشعارات الجهاز» أو بطاقة الإذن).

### 3.5 التشخيص

`select public.push_diagnostics();` يعرض الآن أيضاً:

| الحقل | الدلالة |
|---|---|
| `trigger_new_user` | هل trigger الإشعار على `profiles` منصَّب؟ |
| `admins_count` | عدد مستلمي إشعار «مستخدم جديد» الآن |
| `registered_users` | إجمالي الملفات الشخصية |
| `directory_rpc` | هل دالة دليل المستخدمين موجودة؟ |
| `last_log` | آخر 5 محاولات إرسال (بما فيها `new_user`) مع رمز HTTP من `net._http_response` |

وسجلات الدالة تطبع: `[send-push] request type=new_user` ثم `[send-push] new_user user=… admins=… devices=…` ثم ملخّص `logDelivery`.

## 4) الميزة 2 — دليل المستخدمين الشامل (بحث حي + بدء محادثة)

### 4.1 المشكلة قبل الإصلاح

مربع البحث كان يستدعي `filterContactList()` التي تُخفي/تُظهر **الصفوف المعروضة فقط**؛ وصفوف المشرف تُبنى من `conversations`. المستخدم الذي لم يراسل أحداً قط لا يظهر في القائمة، ويستحيل على المشرف بدء محادثة معه.

### 4.2 الدالة `admin_directory_search(p_query, p_limit, p_offset)`

* `SECURITY DEFINER` + تحقق داخلي: `if v_uid is null or not public.is_admin_user(v_uid) then raise … 42501`.
* `p_query = ''` ⇒ أحدث المسجّلين (`created_at desc`)، وإلا مطابقة جزئية في **الاسم** (`ilike`) أو **البريد** (`ilike`) أو **الهاتف** بأي صيغة (تُجرَّد كل المحارف غير الرقمية من الطرفين، مع تحويل الأرقام العربية/الفارسية، ومنطق «آخر 7 أرقام» لتغطية رمز الدولة `+966` / `00966`).
* **تهريب محارف LIKE** (`\`, `%`, `_`) ⇒ لا يتحوّل البحث إلى نمط مفتوح.
* تُرجع `{ total, limit, offset, query, users: [...] }` — وكل مستخدم يحمل `conversation_id` **إن كانت لديه محادثة قائمة مع المشرف المستدعي** (لتفادي إنشاء محادثة مكرّرة)، مع استبعاد البريد الداخلي `phone.*@users.local`.
* حماية: `limit` محصور بين 1 و200، و`offset ≥ 0`، ولا يُرجِع المشرف المستدعي نفسه.
* فهارس: `pg_trgm` GIN على الاسم والبريد + `created_at desc` (إن لم يتوفّر `pg_trgm` تُتخطّى بأمان بلا فشل الهجرة).

### 4.3 الواجهة

* **الفتح**: تركيز أو كتابة في مربع البحث (للمشرف فقط) ⇒ يُفتح قسم «كل المستخدمين المسجّلين» وتُخفى أقسام المحادثات مؤقتاً (تُعاد عند الإغلاق بزر ✕ أو مفتاح Esc أو بعد فتح محادثة).
* **بحث حي**: `debounce` 220ms لكل حرف، مع تجاهل النتائج المتأخرة (`directoryRequestId`) حتى لا تظهر نتيجة حرفٍ قديم بعد نتيجة الأحدث.
* **عرض النتائج**: صف لكل مستخدم بنفس تصميم صفوف المحادثات مع سطر توضيحي = بيانات التواصل + تاريخ الانضمام (اليوم/أمس/تاريخ)، وشارة «محادثة قائمة» لمن لديه محادثة، وشارة عدّاد الرسائل غير المقروءة.
* **الكل وليس الأوائل فقط**: زر «عرض المزيد (60/…)» يجلب الصفحة التالية ويُلحقها (حد أقصى 200 للصفحة).
* **النقر على أي نتيجة** ⇒ `openConversation()` تُنشئ المحادثة إن لم تكن موجودة ثم تُحدَّث القائمة الفرعية، ويُفرَّغ البحث ويُغلق الدليل.
* **مسار احتياطي**: إن لم تُنفَّذ الهجرة بعد (`PGRST202`/دالة غير موجودة) يعمل الدليل باستعلام مباشر على `profiles` مع `or(...ilike...)` و`range()`، فتُستفاد الميزة قبل تطبيق الهجرة (بمطابقة هاتف أبسط).

### 4.4 Realtime + نقرة الإشعار

* قناة `admin-directory` تشترك في `profiles: INSERT` (للمشرف فقط): تُحدّث الدليل لحظياً إن كان مفتوحاً، وتُظهر تنبيهاً عائماً **قابلاً للنقر**: «👤 مستخدم جديد: <الاسم> — اضغط لبدء محادثة». هذه طبقة ثانية تعمل حتى لو كانت الإشعارات مرفوضة/غير مدعومة على الجهاز.
* **نقرة إشعار FCM**: الـ Service Worker يبني `?user=<id>` (ويمرّر `userId` في رسالة `OPEN_CONVERSATION`)، والموجّه في `js/notification-router.js` يعترف بالهدف المُكوَّن من مستخدم وحده، و`app.js` يفتح/يُنشئ المحادثة فوراً.

### 4.5 الصلاحيات والأمان

* لا كشف بيانات جديد: سياسة `profiles readable by authenticated` تسمح أصلاً لأي مستخدم مسجَّل بقراءة `profiles`؛ الدالة تمنع **غير المشرف** صراحةً (فشل 42501) — مُتحقَّق منه في اختبار PostgreSQL.
* لا تُرجع الدالة توكنات ولا بريداً داخلياً؛ ولا تكتب في أي جدول.
* لا يظهر زر الدليل ولا يُستدعى RPC لغير المشرف (مُتحقَّق منه في اختبار الواجهة).

## 8) الأداء والملاحظات

* الإشعار الجماعي: طلب شبكة واحد + استعلام واحد لتوكنات كل المشرفين (لا N+1)، مع توازٍ محدود (10) وإعادة محاولة للأخطاء العابرة في `sendToAllDevices` — أي أن سلوك تعدّد الأجهزة v2.7 محفوظ كما هو.
* البحث: `ilike` مدعوم بفهرس ثلاثي؛ ومع `p_limit ≤ 200` لا يُحمّل المتصفح أكثر من صفحة واحدة في المرة.
* فشل `pg_trgm` (بيئات قديمة) لا يمنع الهجرة ولا تعطّل البحث — يسقط إلى مسح تسلسلي بسيط.
* `push_delivery_log` يحتفظ بسطر لكل تسجيل (`kind = 'new_user'`) لأغراض التشخيص؛ وهو موجود أصلاً مع سياسة حذف/تنظيف دورية في الهجرات السابقة.

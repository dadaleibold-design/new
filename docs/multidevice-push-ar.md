# أجهزة متعددة لكل مستخدم (FCM) + تتبّع التسجيل — v2.7

> التاريخ: 2026-10-13 — الفرع: `arena/139967f1-new`
> يُكمّل `docs/push-background-root-cause-ar.md` (إصلاح الخلفية في الـ Service Worker).

## 1) النموذج: علاقة واحد-لكثير (موجود مسبقاً، وأُضيف له ما كان ناقصاً)

جدول `fcm_tokens` يحوي **صفاً لكل جهاز/متصفح** لكل مستخدم (`user_id` مفهرس، `token` فريد).
لم نحتج جدولاً جديداً؛ الإضافات:

| العمود | النوع | الغرض |
|---|---|---|
| `device_id` | `text` | هوية ثابتة للمتصفح (`localStorage.wa_device_id`)، لا تتغيّر عند تسجيل الخروج |
| `device_info` | `jsonb` | المنصة، وضع PWA، اللغة، المنطقة، user-agent مقصوص، وقت التسجيل (بلا توكنات) |
| `updated_at` | `timestamptz` | موجود مسبقاً |
| فهرس `(user_id, device_id)` | | لتنظيف صف الجهاز القديم عند التدوير بسرعة |

## 2) ما كان خاطئاً (ومُتحقَّق منه بالاختبار على الكود القديم)

1. **تدوير التوكن لم يُحفظ فوراً.** قرار الكتابة كان يُحسب قبل اكتشاف التدوير؛ مع مزامنة حديثة (< 30 دقيقة) تُتخطّى الكتابة والتوكن الميّت يبقى في الخادم.
2. **تبديل الحساب على المتصفح نفسه لم يُنقل.** مزامنة غير مُجبَرة مع مزامنة حديثة لا تكتب، فيبقى الجهاز مربوطاً بالحساب القديم ولا تصل إشعارات الحساب الجديد.
3. **تكرار الإشعار على الجهاز نفسه.** بعد التدوير يبقى الصف القديم حتى يفشل FCM فيحذفه؛ الجهاز يتلقى الإشعار مرتين.
4. **`fcm_user_id` كان يُكتب قبل نجاح الحفظ.** فشل الشبكة كان يُسقط المحاولة التالية.
5. **الدالة لم تكن تُرجع أي معلومة** عن الإجراء (جديد/تحديث/نقل) فلم يكن ممكناً تتبّع ما حدث.

## 3) ما تغيّر

### قاعدة البيانات — `sql/migrations/2026-10-13_v2_7_device_tokens.sql`
- إضافة `device_id` و`device_info` والفهرس. آمن للتشغيل أكثر من مرة.
- `register_fcm_token(p_token, p_platform, p_device_id, p_device_info)` ← `jsonb`:
  - تُرجع `{ id, action, rotated_removed }` حيث `action ∈ {inserted, refreshed, moved}`.
  - عند التدوير على نفس الجهاز تحذف صفوف **نفس المستخدم** لهذا `device_id` بتوكن مختلف.
  - لا تحذف صفوف حسابات أخرى (أمان: الدالة `SECURITY DEFINER`، ومعرّف الجهاز يمكن أن يكون معروفاً لطرف آخر). الصفوف القديمة لحساب سابق تُحذف عند تسجيل خروجه (حذف بصلاحية صاحب الصف) أو عند رفض FCM للتوكن.
  - تبقى `SECURITY DEFINER` و`search_path = public` ومنح `EXECUTE` للـ `authenticated` فقط.
- `sql/schema.sql` مُحدَّث بنفس البنية للتثبيت الجديد.

**تحقّق فعلي:** شُغّلت الهجرة ودالة `schema.sql` على PostgreSQL حقيقي (18 فحصاً: إدراج، تحديث، تدوير، نقل بين الحسابات، عزل المستخدمين، رفض غير المُصادق، رفض التوكن الفارغ، الرجوع للتوقيع القديم بوسائط افتراضية، الصلاحيات، SECURITY DEFINER).

### العميل — `js/push-policy.js` (منطق نقي) و`js/push.js`
- `decideServerWrite`: الأسباب بالترتيب `forced → token-rotated → user-changed → no-local-token → never-synced → stale-sync → unchanged`.
- `getOrCreateDeviceId` و`buildDeviceInfo`: هوية الجهاز ومعلوماته (حجم محدود، بلا توكنات).
- `syncPushToken`: يكشف التدوير وتغيّر المستخدم **قبل** القرار، ويحدّث `fcm_user_id` بعد نجاح الكتابة فقط، ويطبع الإجراء المُرجَع.
- الرجوع إلى `from("fcm_tokens").upsert(` يبقى لتوافق ما قبل الهجرة.

### الخادم — `supabase/functions/send-push/index.ts`
- `loadDeviceTokens` يقرأ `device_id` و`device_info` ويطبع عدد أجهزة المستلم:
  `[send-push] recipient=xxxxxxxx… devices=3 [android-pwa/1a2b3c4d, web/…]`
- الإرسال إلى **كل** التوكنات النشطة للمستلم بتوازٍ محدود (10)، مع إعادة محاولة للأخطاء العابرة (429/5xx/شبكة)، وحذف التوكنات الميّتة فقط (UNREGISTERED / غير صالح).

> **انحراف عن الطلب الحرفي:** طلبتَ `admin.messaging().sendEachForMulticast`. هذه واجهة Admin SDK في Node، بينما Edge Function تعمل على Deno وتستخدم FCM HTTP v1 الذي يقبل رسالة واحدة لكل طلب ولا يملك نقطة multicast. النتيجة العملية واحدة: كل توكنات الحساب تُرسل إليها في الدفعة نفسها، مع نتيجة لكل توكن.

## 4) التتبّع (console)

| الموقع | الرسالة |
|---|---|
| الخادم، لكل إشعار | `[send-push] request type=…` |
| الخادم، لكل دفعة | `[send-push] recipient=… devices=N [...]` |
| الخادم، ملخص | `logDelivery` (نجاح/فشل/محذوف) |
| العميل، قبل الكتابة | `[FCM] تسجيل جهاز للمستخدم … device=… platform=… سبب=…` |
| العميل، بعد النجاح | `[FCM] token inserted|refreshed|moved — user=… device=… removedRotated=N (…suffix)` |
| العميل، بلا كتابة | `[FCM] التوكن مُسجَّل مسبقاً — لا حاجة للكتابة (unchanged)` |
| العميل، عند الاستلام | `[FCM]` / `[push-sw]` (من Task A) |

لا تُطبع التوكنات كاملة، فقط آخر 8 خانات.

## 5) الاختبارات

- `tests/multidevice-push.mjs`: منطق القرار (يشمل الانحدارين 1 و2)، هوية الجهاز، وفحوص ثابتة للعقد والترتيب.
- `tests/push-sync-behavior.mjs`: يشغّل `syncPushToken` الحقيقي بمحاكيات Firebase/Supabase: تدوير، تبديل حساب، فشل ثم إعادة، جهازان لحساب واحد، رجوع للـ upsert، وسجلات. **على الكود القديم يفشل 7 من 8** (يمرّ فقط «بلا تغيير → لا كتابة»).
- أُضيفا إلى `npm test`.

## 6) النشر

1. طبّق `sql/migrations/2026-10-13_v2_7_device_tokens.sql` على Supabase (قبل نشر الواجهة).
2. أعد نشر Edge Function `send-push`.
3. الواجهة تُحمَّل بعد تحديث `sw.js` (الكاش v15 من Task A).

## 7) حدود معروفة

- لم يُختبر على أجهزة حقيقية متعددة ولا على FCM الفعلي؛ الاختبارات على محاكيات ودالة SQL على PostgreSQL.
- حالة متصفح مشترك بين حسابين دون تسجيل خروج (جلسة منتهية) تُبقي صفاً لحساب سابق حتى رفض FCM له أو تسجيل خروجه.
- التوكنات القديمة جداً التي لم يُعد تسجيلها تبقى حتى يرفضها FCM؛ لا حذف زمني تلقائي.
